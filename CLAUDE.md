# HabeshaMatch: Claude Code project guide

Read this file fully at the start of every session. It is the source of truth for product rules, stack, and conventions. If a request conflicts with this file, stop and ask before proceeding.

## What we are building

A mobile dating app (iOS + Android) for the Eritrean and Ethiopian community worldwide, focused on serious relationships and marriage. Preference-driven matching first, with a small daily swipe section as a secondary feature.

The owner is a technical project manager, not a full-time mobile developer. Explain what you are about to do before large changes, keep changes small and reviewable, and commit after each working step.

## Stack

| Layer | Choice |
|---|---|
| Mobile app | React Native + Expo (managed workflow), TypeScript, expo-router |
| Backend | Supabase: Postgres, Auth (email OTP, Google, Apple; phone verification), Realtime, Storage, Edge Functions |
| SMS (phone verification) | Twilio (configured inside Supabase Auth) |
| Email (sign in codes) | Custom SMTP in Supabase Auth before launch (the built-in sender is for testing only) |
| Subscriptions | RevenueCat over App Store and Google Play billing. Never Stripe for in-app purchases |
| Push notifications | Expo Notifications |
| Admin panel | Next.js 16 web app in `admin/`, hosted on Vercel, same Supabase project. Setup and live admins: `docs/ADMIN.md` |
| Images | Compress and resize on device with expo-image-manipulator before upload |

## Sign in and phone verification

Two separate steps. Do not merge them or reorder them.

1. **Sign in** (creates the account on first use): email with a 6 digit code (`signInWithOtp({ email })`, then `verifyOtp({ type: 'email' })`), Sign in with Google, and Sign in with Apple. Phone is NOT a sign in method: phone sign up is disabled in Supabase Auth (`[auth.sms] enable_signup = false`).
2. **Phone verification** (once per account, first onboarding step, no skip): `updateUser({ phone })` texts a code, then `verifyOtp({ phone, token, type: 'phone_change' })` confirms it and sets `auth.users.phone`. To send a new code, call `updateUser({ phone })` again (the resend endpoint is blocked while phone sign in is disabled). A number linked to another account fails with `phone_exists`.

Rules:
- Phone verification must finish BEFORE the residence step and before the `profiles` row is created, because `enforce_residence_rules` reads `auth.users.phone` to check the local-tier prefix. The database enforces this: inserting a profile without a confirmed phone raises `phone_not_verified` (trigger `profiles_phone_verified`).
- A phone counts as verified when `user.phone` and `user.phone_confirmed_at` are both set (`isPhoneVerified` in `mobile/lib/auth.ts`). Once verified, never ask again.
- Routing follows server state, so closing the app resumes at the same step: no session goes to `(auth)`; signed in without a verified phone sees only the phone screens; verified without a `profiles` row sees only the profile wizard (`(onboarding)/profile-setup.tsx`); with a profile, photos come next (at least 2, `MIN_PHOTOS` in `mobile/lib/verification.ts`), then the verification selfie (`(onboarding)/selfie.tsx`), then preferences (`(onboarding)/preferences.tsx`), then the review screen (`(onboarding)/review.tsx`) until an admin approves the member (see Member approval). `(tabs)` opens only when the member is approved AND has preferences. Photos and preferences stay reachable afterwards from the Profile tab for editing. Guards live in `app/_layout.tsx` and `app/(onboarding)/_layout.tsx` (`Stack.Protected`); progress comes from `useSession()` (`profileStatus`, `photoCount`, `hasPreferences`, `approved`, `accountStatus`, `verification`).
- The profile wizard keeps a draft in encrypted device storage (`lib/profileDraft.ts`) and creates the `profiles` row once, at the end. Its residence step reads `local_tier_countries` and `app_config.location_change_cooldown_days`; it mirrors the local-tier phone rule only to explain it early, the database makes the final check.
- Phone confirmations must be ON everywhere. If off, `updateUser({ phone })` saves the number without a code, which would let anyone claim a local-tier number. Locally: `[auth.sms] enable_confirmations = true` in `supabase/config.toml`. Remote: the dashboard toggle (Authentication > Sign In / Providers > Phone > Enable phone confirmations) is the ONLY control; it is deliberately left out of `supabase/remote-auth`, because the CLI reads and writes it inverted for the remote project. Do not trust `config diff` for this setting; confirm by behaviour (entering a phone number shows the code screen, and `auth.users.phone_change_sent_at` is set).
- Email codes use the template in `supabase/remote-auth/templates/sign_in_code.html` (inside remote-auth because `config push` only reads files inside its workdir; the local config points there too) for both the confirmation (new user) and magic link (returning user) emails. `[auth.email] otp_length = 6`.
- Test phone numbers (code `123456`, no SMS sent) are listed under `[auth.sms.test_otp]` in `supabase/config.toml`.
- Twilio credentials: on the remote project they are entered in the Supabase dashboard only. In `supabase/config.toml` they are `env()` references, filled locally from `supabase/.env` (copy `supabase/.env.example`; placeholders are fine locally).
- Remote auth settings are pushed ONLY from `supabase/remote-auth/` (`supabase config push --workdir supabase/remote-auth --project-ref <ref>`), which has no Twilio section so it can never overwrite the dashboard values. Never push the main `supabase/config.toml`: an unset `env()` is pushed as its literal text. Never run `config push` for auth without the owner's go-ahead; run `supabase config diff` with the same flags first.
- After ANY auth change in the Supabase dashboard (SMTP, providers, Twilio), rerun `supabase config diff --workdir supabase/remote-auth --project-ref <ref>` and check in the dashboard that "Enable phone confirmations" is still on. Saving the Phone provider page has switched it off before.
- Postponed launch work (Twilio, domain, Resend domain, Google and Apple) is tracked in `docs/LAUNCH_CHECKLIST.md`.
- Google and Apple use native sign in (`signInWithIdToken`), which needs a development build; email works in Expo Go.

## Product rules (enforced in the database, mirrored in the UI)

The database migration in `supabase/migrations/` already implements these. The app must call the RPC functions, never re-implement the rules client-side.

### Tiers
Tier is decided by declared permanent residence (`profiles.residence_country_code`), not current location or IP.

| | Free (abroad) | Local | Premium (abroad, paid) |
|---|---|---|---|
| Who | Lives outside local-tier countries | Lives in ET, ER, UG, SD, KE, AO | Abroad user with active subscription |
| New conversations per day | 5 | Unlimited (safety cap 50) | Unlimited (safety cap 50) |
| Receive and reply | Unlimited | Unlimited | Unlimited |
| Swipes per day | 10 | 10 | 25 |
| See who liked you | Count only (blurred) | Count only | Full list |
| Suggested section | No | No | Yes |
| Daily picks | No | No | Yes |
| Undo last swipe | No | No | Yes |
| Blue tick | Every member (all members are verified before they can take part) |

- Local-tier countries live in table `local_tier_countries`. Never hardcode the list.
- Declaring a local-tier residence requires a verified phone number with a local-tier prefix (see Sign in and phone verification).
- Residence can change once every 30 days.
- Pricing: 1 month $9.99, 3 months $24.99, 6 months $39.99 (configured in the stores and RevenueCat, not in code).
- All limits live in table `app_config`. Never hardcode a limit in the app; read from `get_my_limits()`.
- There is no paid badge. Never display who is paying.

### Matching
- Preferences are saved by `mobile/lib/preferences.ts`: `preference_core` (gender, age range) always; one `preference_items` row per attribute the user sets, marked hard ("Must have") or soft ("Nice to have"); attributes left as "Any" have no row. "Where they live" is a searchable multi-select of countries (`country`). The `residence_type` (abroad / back home) attribute still works in the database but the app no longer offers it; saving preferences removes an old one. Income is "at least" a bracket, saved as `{"min": "<income_range_t>"}`; "prefer not to say" or no answer never meets it.
- **Hard preferences:** deal-breakers. Gender and age range are always hard (`preference_core`). Other attributes (`preference_items`) are marked hard or soft by the user.
- **Meets My Criteria:** both users pass each other's hard preferences AND the candidate meets at least `soft_match_threshold` of the viewer's soft preferences. Ranked by soft score. The threshold is currently 0 (migration `20261017000002`), so nice-to-haves only rank and never hide anyone while the community is small; raise it later in `app_config`. Anyone here can be messaged directly, no approval. Nobody is hidden for being inactive; ordering does the work (migration `20261024000002`, `get_meets_my_criteria(limit, offset, sort)`): people you already chat with are left out (they are in Messages), people you passed on in Swipe go last, and ties break with a daily shuffle that differs per viewer so the same few people are not on top for everyone. Order: active within `discover_recent_days` (7) first, then within `discover_inactive_days` (30), then the rest; best nice-to-have score first within each. A Filter button on Discover narrows the list to chosen residence countries (`p_countries`), picked from the countries the member's current matches live in, with counts (`get_meets_my_criteria_countries()`); it never widens or changes their preferences, and resets when the app restarts. Phase two ideas, once there are many members: "Active today" and "Near me" sorting.
- **Suggested (premium):** the viewer meets the candidate's hard preferences, the candidate does NOT meet the viewer's. The viewer may make an exception and message directly. Shown in the For you tab (see below) with the line "These people are looking for someone like you, but don't match all your must-haves." Everyone sees how many (`get_suggested_count()`, a number only).
- **Suggested stays short** (migration `20261024000004`, one rule in `is_suggested_for()`): people you chat with, people you passed on in Swipe, and people you removed yourself are left out. "Not for me" is a ✕ on each Suggested tile (with a few seconds to Undo) and a button on their profile when opened from Suggested (`/profile/[id]?from=suggested`); it is quiet (they never know) and only affects your Suggested list (`suggested_dismissals`, changed only via `dismiss_suggestion()` / `undo_dismiss_suggestion()`). The Suggested badge inside For you counts only people new to the list since the section was last opened (`get_suggested_count(since)`, new = approved as a member since then); the total shows in the intro line and on the paywall teaser.
- **Daily picks (premium):** `daily_picks_per_day` (5) people a day who fit both ways, have no chat with you and you have not passed on, best nice-to-have score first; people picked in the last `daily_picks_repeat_after_days` go to the back. Made by `generate_daily_picks()` every day at 00:05 UTC (Supabase Cron job `generate-daily-picks`, migration `20261024000000`), and on demand by `get_daily_picks()` when a member has none yet today. Shown under Picks in the For you tab; tapping opens the profile. Someone you start a chat with drops out of the picks.
- **Undo (premium):** one step back on the Swipe screen (`undo_last_swipe()`), not for a swipe that became a match. Everyone else's Undo button opens the paywall.
- **Core messaging invariant:** you can only start a chat with someone whose hard preferences you meet. Nobody ever receives a first message from someone who fails their deal-breakers.
- **For you tab** (`app/(tabs)/for-you.tsx`, between Swipe and Messages): everyone who might want you, as three sections, each with a rose count badge: Liked you (`get_likes_received_count()`), Picks (today's picks, Premium only) and Suggested (`get_suggested_count()`). All three lists are Premium; everyone else sees the real count, a short explanation and See Premium (local tier included, per the tier table), never the people, and never blurred photos. Premium members see grids of profiles; Liked you also has a Like back button opening the `liked-you` card stack (swipe right to match). The tab itself is badged with what is NEW since the member last opened it, then clears, like unread messages: new likes + people new to Suggested (approved since then) + today's picks until opened that day (`get_for_you_new_counts(since)`, numbers only). When they last opened it is kept on the phone (`mobile/lib/forYou.ts`). Never badge totals that don't change: an always-lit badge gets ignored.
- **Messages tab layout:** a NEW MATCHES row at the top (conversations with no messages yet; they move into the list once someone writes), then conversations.
- **Swipe section:** ignores criteria except gender and age range, which must fit in both directions. Mutual like opens a chat that does not count toward the daily limit. Deck shows same country first, then same region type (diaspora or home), then the rest.

### Safety (required for App Store approval)
- 18+ only, enforced at profile creation.
- Block and report available from every profile and chat (`components/SafetyMenu.tsx`, the "⋯" button). Reporting offers "Also block" (on by default). A block hides both people from each other everywhere (discovery, profiles, photos, inbox, messages; `get_profile` too). Blocked people are listed under Profile, Blocked people (`get_my_blocked_users()`, first names only) with Unblock. The server clears moderation fields on new reports (trigger `reports_defaults`).
- Photos start as `pending` and are invisible to others until an admin approves them. Files are in the PRIVATE Storage bucket `photos` at `{user_id}/...` (JPEG only, 5 MB); storage policies let users write and delete only their own folder and read others' files only when the `photos` row is approved and the owner is discoverable to them. View photos with signed URLs. Compress on device (`mobile/lib/photos.ts`) before upload; each photo also gets a ~400px thumbnail at `{path}.thumb.jpg` (`photo_thumb_path()`), readable by others exactly when the photo is. Lists use thumbnails (with a fallback to the full photo); profile pages use full photos. Reorder only via `reorder_my_photos(ids)`; owners have no UPDATE policy on `photos`.
- **Member approval (mandatory, free):** every member is checked by a person before they can take part. They upload at least 2 photos, then a live front-camera selfie, never from the gallery (`lib/verification.ts`), stored in the PRIVATE bucket `verifications` at `{user_id}/...` (owner and admins only). That creates a `verification_requests` row (trigger `verification_submit`: needs 2 non-rejected photos, else `two_photos_required`; one pending request per member). In the admin panel (New members), an admin checks the selfie matches the photos: Approve sets `is_photo_verified` (blue tick), approves the photos not marked as a problem, and needs at least 2; Reject needs a reason (`rejection_reason`, shown to the member on the review screen) and can reject individual photos. The member then fixes photos and sends a new selfie.
- An approved member (`is_approved_member()`): account active, `is_photo_verified`, and at least one approved photo. Until approved, a member is invisible to everyone (`is_discoverable`) and cannot discover, swipe, like, start chats or send messages (`require_approved_user()` raises `approval_pending`; the `messages` insert policy checks it too). Photos added later by approved members go to the admin New photos queue.
- In-app account deletion: Profile tab, Delete account, confirmed twice (sheet, then type DELETE). Calls edge function `supabase/functions/delete-account` (`withSupabase({ auth: 'user' })`, JWT verified), which removes the caller's files in every bucket and deletes their auth user; everything else cascades. Deploy with `supabase functions deploy delete-account --project-ref <ref>` (owner's go-ahead).
- Profile tab = settings: edit profile (`app/edit-profile.tsx`, reuses `components/ProfileFields.tsx`; date of birth and gender are not editable), photos, preferences, blocked people, notifications (Prompt 5.2), privacy policy, terms, support (`mobile/lib/links.ts`), log out, log out of all devices (`signOut({ scope: 'global' })`), delete account.
- Text-only messaging, max 2000 characters. Messages are sent with an app-chosen id (so the live echo is not shown twice; a duplicate-id error means it was already sent). The server sets `created_at` and `read_at` for app users (trigger `messages_defaults`). Live updates use Supabase Realtime on `messages` (RLS decides who receives what); Realtime can take a few seconds to start after subscribing, so the app refetches when a channel connects, when the app returns to the foreground, and when the inbox shows a newer message than the open chat.

### Profile fields
Deliberately not collected: ethnicity or region within Eritrea or Ethiopia (sensitive, invites division and abuse), body type, politics, zodiac. Religiosity ("how religious") was considered and left out for now.
Name, date of birth (age shown, never DOB), gender (male/female), height (stored in cm, shown as ft/in or cm by region), origin (Eritrea/Ethiopia), current city, permanent residence country, religion (single choice), languages (up to 8, stored as ISO 639 codes from `mobile/lib/languages.ts`, never free text), relationship intent (single choice), yearly income range in USD (`income_range`, includes prefer not to say; not shown to others yet), education level (`education_level`, includes prefer not to say), family and lifestyle (marital status, has children, wants children, smoking, drinking, exercise; all usable as preferences), occupation (optional, 60 chars), interests (up to 8 codes from `mobile/lib/interests.ts`, never free text), bio (500 chars), open to relocating, open to long distance, up to 6 photos.

## Conventions

- TypeScript strict mode. No `any` without a comment explaining why.
- Every schema change is a NEW migration file. Never edit an applied migration.
- After any migration: regenerate types, run `supabase/tests/rules_smoke_test.sql` locally, fix any FAIL.
- Never put the Supabase service role key, Twilio, or RevenueCat secret keys in the mobile app. Secrets live in Supabase secrets or Vercel env vars only.
- Admin panel rules: every page and server action starts with `requireAdmin()` (`admin/lib/auth.ts`, checks the `admins` table); the secret key client is `server-only` (`admin/lib/supabase/admin.ts`); every moderation decision goes through `logAction()` into `moderation_actions`. Admin-only database functions (`admin_search_users`, `admin_stats`) are executable by `service_role` only. Keep `admin/lib/database.types.ts` in sync with `mobile/types/database.ts` when regenerating types.
- Build for slow, expensive mobile data: compress images (max 1080px, ~70% JPEG), use thumbnails in lists, paginate everything, cache with React Query (`mobile/lib/queryClient.ts`, cleared on sign out or account switch).
- Local test data: after `supabase db reset`, run `node supabase/scripts/seed-photos.mjs` so seed profiles have photo files.
- Choosing the backend while developing: `npm run start:local` (in `mobile/`) points the app at the Supabase on this Mac using its current Wi-Fi address (it changes now and then) and starts Expo; `npm run start:live` points it back at the live project.
- Writing style in UI copy: no em dashes.
- Small commits with clear messages. Work on a branch per feature, merge to `main` when it works.
